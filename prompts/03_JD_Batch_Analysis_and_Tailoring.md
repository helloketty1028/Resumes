# 工具 C：JD Batch — 批量分诊、定位、生成与一致性检查
> 用途：一次拿到一组 JD，先批量评估哪些值得投，再对选中的批量生成简历。
> 与工具 A 的关系：A 处理单个 JD；C = 批量分诊 + 共享包调度 + 跨简历一致性 + 合并回灌。起草与审计规则沿用 A。
> 版本：v1.1 · 2026-10-26 · 省 token 版：分诊不开子代理；生成阶段用共享包 + fork；审计、冷读一个代理处理多份；报告设预算。旧版见 `prompts\archive\`。

---

## 00. 使用方式（分会话调度）

| 会话 | 发送内容 | 做什么 | 结束于 |
|---|---|---|---|
| ① 分诊 | `请读取并执行 C:\Users\surface\resumes\prompts\03_JD_Batch_Analysis_and_Tailoring.md`，`模式：triage`，附 JD 列表 | 阶段一、阶段二 | ★ C1、★ C2，产出 `Batch_Triage.md`、`Batch_Positioning.md` |
| ② 生成（新会话） | 同一句，`模式：generate`，`批次：applications\_batches\<批次名>`，`选中：#1, #4, #6` | 阶段三至六 | ★ C3、★ C4 |
| ③ 回灌（新会话） | 工具 B，材料指向 `Batch_Fact_Update_Proposal.md` | 写事实库 | 工具 B 的审批门 |

- 每个 generate 会话完整生成 **3–5 份**；选中更多时，分几个 generate 会话。
- JD 不超过 3 份时，可以用 `模式：full` 在一个会话里跑完。
- 不要在同一个会话里连跑多个批次。

## 2. 阶段一：批量分诊（主会话直接做，不开子代理）

- 按工具 A §2A R-A1 的"阶段一"清单读**一次**，所有 JD 共用；JD 逐份过，不为每份 JD 重读事实库。

对每份 JD：

1. **提取基本信息**：公司、职位、Job ID、地点、合同类型、截止日期；提取不到的标"待确认"。
2. **与已有申请查重**：列出 `applications\` 下的目录名（不读内容），看是否已有同公司或同职位；有则提示，并说明可否复用其简历作底稿。
3. **分类**：Family（ATL / SM / TPM）× Lens（BNK / INT），写出判断依据（05 §2）。
4. **Fast-reject 与 Eligibility**（05 §3–§4）：命中任何一项都单列。重点核对工作准证 / PR、强制认证（PMP、TOGAF、AWS 等）、银行年限、语言、地点。
5. **Required 要求逐项对照证据**（05 §5），统计 Direct / Transferable / Gap / Unverified 各几项，列出**阻断项**（没有证据且 JD 写明必须的）。
6. **定性档位**（不打分、不给百分比、不估面试概率，D-03）：

   | 档位 | 含义 |
   |---|---|
   | **A** | Required 基本都有 Direct 或强 Transferable，无 Eligibility 缺口，定位清晰 |
   | **B** | 可投，但有明确 gap，需要靠定位和措辞诚实处理 |
   | **C** | 勉强：定位偏离我的主线，或多项 Required 只有弱证据 |
   | **X** | 建议不投：命中 fast-reject、Eligibility 缺口，或需要我没有的核心领域 |

   档位必须写理由，并注明依据哪几条证据。
7. **建议简历方案**：用哪个 Family × Lens；底稿取自哪个已有申请或 `Resumes\` 下哪份 LIB V5；预计工作量（可直接微调 / 需重新取材）。

**汇总输出 `Batch_Triage.md`**（预算：每份 JD 一行；单份的补充说明不超过 3 行）：

| # | 公司 | 职位 | 档位 | Family×Lens | Required 证据统计 D/T/G/U | 阻断项 | Eligibility 风险 | 与旧申请重复 | 建议动作 |
|---|---|---|---|---|---|---|---|---|---|

同时给出：
- **共性问题表**：多份 JD 共同涉及的未决事实合并成一条，标注涉及哪几份 JD，只问我一次。每条附"不回答时的默认处理"。
- **批次观察**（≤10 行）：这批 JD 的定位是否分散？是否值得集中精力在其中 3–5 份？只给判断依据，不替我决定。

**★ 审批门 C1**：我选择进入下一阶段的 JD（可调整档位建议）、回答共性问题。

## 3. 阶段二：批量定位与取材

对选中的 JD，**用一张"定位卡"一次呈现**，不逐份打断我。写入 `Batch_Positioning.md`，每张卡不超过 12 行：

| 项 | 内容 |
|---|---|
| Headline | 取自 02 §7，写明是否针对本 JD 调整 |
| Summary 主线 | 一句话叙事主线 + 对位 JD 的哪 2–3 个 Required |
| Selected Achievements | 6–8 条，按 ID 排序，写明为什么放这条 |
| 压缩 / 省略 | 哪些经历压缩或省略，原因 |
| Gap 处理 | 每个 gap 的诚实写法，禁止把 Transferable 写成 Direct |
| 关键词映射 | JD 原词 → 记录中的词 → 证据 ID（有证据才用） |
| IDs | 本简历要用的全部 PA / X 编号（阶段三据此建共享包） |
| 待我确认 | 只列会改变定位或事实的问题 |

**★ 审批门 C2**：我逐份确认或调整定位卡。`triage` 模式到此结束：请我新开会话，用 `generate` 模式继续。

## 4. 简历可读性标准

**R1–R5 已写入事实库规则（2026-10-20，D-13），按其执行，本文件不再重复：**
- 三类读者（HR、用人经理、ATS）、首页回答三问、JD 前 5 项 Required 在首页有证据、通俗语言 → `01 §6A`
- Bullet 长度与结构、数字个数 → `01 §6` 的 Bullets / Numbers 行
- 拼写（英式，新加坡标准；JD 目标职位名按原文引用）、Summary 长度（约 3 个短段）→ `01 §6` 的 Spelling / Summary length 行
- 版面限值（bullet ≤3 行、段落 ≤4 行、首页构成）与渲染检查 → `04 §3A`、`04 §6`，用 `ctx.py stats` 检查

阈值标 🔶。渲染结果超限、又无法在不丢失 locked 措辞或限定词的前提下压缩时，列入汇报交我决定，不得为凑限值删除限定词。

**R6 冷读测试（Cold-read）— 每份终稿必做（本工具专有；01 §8 暂未收录）**
- 由**一个**普通子代理完成，用较小模型（`model: sonnet` 或 `haiku`），依次读完本批所有终稿。
- 只提供：每份简历的 pdftotext 文本 + 对应 JD。**不提供事实库、共享包和起草过程，不看页面截图。**
- 让它依次扮演：
  (a) **Recruiter，限时 30 秒**：他是谁、什么层级、最近的角色；与 JD 最匹配的 3 点；最大疑虑；哪些句子读不懂或过于技术。
  (b) **Hiring manager，约 3 分钟**：能否胜任、有无硬伤、会追问什么、是否愿意面试。
- 判定：Recruiter 说不出 3 条匹配点，或指出超过 2 处读不懂，必须回改。
- **冷读意见只用于措辞、排序和删减，不得引入新事实。** 如果意见涉及我没有记录的事实，转为回灌候选项，由我决定。冷读评审员的意见是可读性证据，不是事实证据。
- 每份写入申请目录的 `Readability_ColdRead.md`，不超过 300 词。

## 5. 阶段三：批量生成（共享包 + fork）

1. **新会话启动（generate 模式）**。主会话只做调度：不起草、不写长报告、不读整份事实库文件。
2. 只读 `Batch_Positioning.md` 中选中 JD 的定位卡，以及各份 `JD.md`。
3. **建共享包**：运行 `python3 tools/ctx.py pack --ids <各卡 IDs 的并集> --out applications\_batches\<批次>\context_pack.md`，然后读一次 `context_pack.md`。这是本会话唯一一次读事实库。
   - 共享包是源文件章节的逐字摘录，包头记有版本和校验值；它是派生缓存，不是事实来源。
   - 起草前和 ★ C3 前各运行一次 `python3 tools/ctx.py verify <context_pack.md>`；结果是 STALE 就停下告诉我，重建后再继续。
   - 共享包超过约 30K token 时告诉我，建议拆成两个 generate 会话。
4. **起草用 fork 子代理**（`subagent_type: fork`），每份 JD 一个：
   - fork 继承主会话里已有的共享包和定位卡，**不再读事实库**；只有共享包缺某个 ID 时，才用 ctx.py 补读那一节。
   - 先启动 1 个，它开始运行后再并行启动其余（同时不超过 4 个），让后面的 fork 命中缓存。
   - 任务说明只写：JD 目录、定位卡编号、输出文件名，以及"按工具 A §4 起草，按 §2A 执行"。
   - fork 内的流程：起草 → `ctx.py stats` 自检 → 修正一次 → 写文件 → 回传不超过 150 字（文件路径、页数、stats 结论、待我决定的事项）。
   - 当前环境没有 fork 类型时，改用普通子代理：任务说明的**第一段逐字相同**（"先读 context_pack.md，不读其他事实库文件"），JD 特有内容放在最后。
5. 输出目录、文件名同工具 A §4：`C:\Users\surface\resumes\applications\[YYYY-MM-DD]_[Company]_[Role]\`，`wilson-2026_[Family]_[Lens]_[Company]_V1_0_0_draft.docx`。不覆盖任何已有文件。

## 6. 阶段四：审计（一个代理审多份）

- 审计用**普通子代理**，不用 fork：fork 会继承定位卡和调度上下文，影响独立性。一个审计代理依次审 3–5 份：
  - 先汇总这几份简历引用的 ID 并集，按工具 A §2A R-A1 的"审计"清单从源文件读**一次**；不读 `context_pack.md`。
  - 审下一份时，用 SendMessage 续用同一个审计代理，不重开、不重读。
  - 执行工具 A §5 的全部要求；报告按 R-A4 的预算。
- 需要修改的 FAIL / REVIEW 项，用 SendMessage 交回对应的起草 fork 修正（它保留着上下文），不重新起草。
- 冷读按 §4 R6 执行。

## 7. 阶段五：跨简历一致性检查（批量专有）

同一批简历会由不同的 HR 和猎头看到，甚至互相比对，背调更会交叉核对。

- 只抽取每份简历的雇主行、职位行、日期、headline 和含数字的句子（pdftotext + grep），不读全文；历史简历只比对最近 5 份已投递的终稿。
- 对照表：

| 事实项 | 简历 1 | 简历 2 | … | 历史简历 | 事实库值 | 是否一致 |
|---|---|---|---|---|---|---|
| 各段职位名 / 日期 | | | | | 02 §2 | |
| 团队规模 | | | | | 03 §0A | |
| 关键数字 | | | | | 03 §0A | |
| 所有权动词（同一成就） | | | | | 03 / 01 §4 | |
| Headline、联系方式、姓名写法 | | | | | 02 §1, §7 | |

- 不一致且不是 Lens 造成的有意取舍，必须修正。
- 与已投递的历史简历不一致的，单列提示（可能涉及背调风险），由我决定是否需要补充说明。
- 输出 `Batch_Consistency_Check.md`：只列不一致项和统计，一致的不逐行列出。

**★ 审批门 C3**：交付各份红字草稿 + 审计报告 + 冷读结果 + 一致性表。我逐份确认或修改；批准后生成全黑终稿 `wilson-2026_[Family]_[Lens]_[Company]_V1_0_0.docx` 和 PDF。

## 8. 阶段六：合并回灌候选（去重）

- 汇总所有 JD 过程中产生的事实候选项（我在会话中新确认的事实、审计发现的冲突、需要更正的旧说法），**同一事实只出现一次**，注明来自哪几份 JD。
- 按工具 A §5A 的格式和规则逐条给出建议 Y / L / Q / N 及理由，风险项标"⚠ 背调敏感"。
- **★ 审批门 C4**：我逐条选 Y / E / Q / L / N；**未明确选中的一律 N（默认不回灌）**。
- 决定结果写入批次目录的 `Batch_Fact_Update_Proposal.md`；只有 Y / E / Q 的条目交给工具 B（`场景：申请后回灌`，材料指向该文件，新开会话）。
- 本工具不写事实库。

## 10. 异常处理

- 某份 JD 读取失败（登录墙等）：标"待补充"，请我粘贴文本，不阻塞其他 JD。
- 某份 JD 内容过短：照常分诊，标"JD 不完整"，档位只能给到 B 或以下。
- 选中的 JD 超过 5 份：分几个 generate 会话，先做档位 A、再做 B。
- 共享包 STALE：停止，告诉我，重建后继续。
- 渲染检查无法执行：明说"未验证"，不得声称版面已检查。
- 子代理之间的结论冲突：并列呈现，交我决定，不自行取舍。
