## 3. 第一步：差异识别

逐项对比新材料与现有事实库：

| 临时 ID | 类型 ADD / CORRECT / CLARIFY / RESTRICT / RETIRE | 关联现有 ID | 现有表述（原文） | 建议表述 | 来源与日期 | 建议图标 | 所有权 | 目标文件 §章节 | 影响的现有 claim / 简历 | 冲突或待问 |
|---|---|---|---|---|---|---|---|---|---|---|

**证据规则**
1. 生成的简历**不是证据**：只能用来定位 claim，不能证明 claim。
2. JD 原文、子代理或其他 AI（含 ChatGPT）的输出不是证据。
3. 只有我的明确确认（记 `[CONF 日期]`）或一手文档才能升为 ✅。
4. 个人贡献、团队贡献、项目整体结果、业务结果分开记录；数字写明单位、基线、时间范围，并区分实测与估算。
5. 推断最多标 🔶，不得升 ✅；缺失的日期、技术、指标、职责不得补写。
6. 新旧冲突：两版都保留，标 ⚠️，登记 CF-xx，问我，不替我选。

## 4. 第二步：结构化记录

项目类事实（✅ / 📄）按 03 现有条目结构补全：
背景 · 雇主与期间 · 我的角色与所有权等级 · 问题 / 挑战 · 行动与决策 · 实际使用的技术 · 结果与度量（引用 Metrics Bank）· 来源 · 状态 · Family×Lens 相关度 · safe resume wording · interview angle（STAR，仅限有证据部分）。

技能类事实：写使用场景、证据锚点（雇主 + 期间）与深度，不因为 JD 出现过就添加。

同一事件不拆成多条近似重复记录，除非贡献或结果确实不同。

## 5. 审批门（修改任何文件之前）

输出 `Fact_Library_Update_Review.md`，分四组：

- **A. 可批准的更新**（证据充分）
- **B. 需要我回答的问题**（每条附"不回答时的默认处理"）
- **C. 只能记为推断 / 不入库的内容**
- **D. 可能影响已投递简历的更正**

**→ 停止，等我逐条决定。** 每条给出：精确的修改前 / 修改后文本、目标文件与章节、影响面。决定码：

| 码 | 含义 |
|---|---|
| **Y** | 按提议文本入库 |
| **E** | 按我修改的文本入库（我会给出文本） |
| **Q** | 不当作事实，仅登记为 fact-check 的待确认问题 |
| **N** | 不入库（保留在审查报告里留档） |

规则：
1. 用 AskUserQuestion 让我选：≤ 4 条逐条问；更多时按目标文件分批，multiSelect 勾选要入库的。我也可以直接回复，例如 `A1 Y, A2 E（改成……）, A3 N, 其余 N`。
2. **默认 N**：未被我明确选中的条目不入库，也不改任何文件。"批准全部"只在我明确说出这四个字时才算。
3. 来自工具 A 的候选项，若我在 A 的 5A 已决定 N / L，则不再重复提出；已决定 Y / E / Q 的仍在这里复核一次**具体措辞**（A 决定"要不要"，B 决定"怎么写"）。
4. 对 ⚠ 背调敏感项（职位、日期、团队规模、Metrics Bank 数字、保密项），额外让我确认原始依据，不接受"大概"。
5. 所有未入库条目保留在 `Fact_Library_Update_Review.md` 末尾的"未采纳"表中，注明我的决定和日期，方便日后翻查。

## 6. 应用已批准的更新

1. **修改前快照**：把将要修改的文件复制到 `master\v2.0-draft\archive\snapshot_[YYYY-MM-DD]_[topic]\`。
2. 只改相关文件和章节，外科式修改，不重写无关内容。
3. **不删除历史**（01 §2 rule 5）：被替代内容移入该文件的 retired / superseded 表，注明替代条目与日期。
4. fact-check 文件：新增决策 D-xx、关闭已答复的 FU / OQ、登记新问题。
5. 每个被修改的文件：版本行升 minor 版本、更新日期、change log 写一条。
6. 跨文件一致性：搜索新旧 ID 与关键措辞，确认 02 / 03 / skills / fact-check 之间无矛盾、无重复全文。
7. 回读修改后的文件，确认已保存到正确目录。
