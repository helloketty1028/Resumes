# 工具 C：JD Batch — 批量分诊、定位、生成与一致性检查
> 用途：一次拿到一组 JD（2–8 份），先批量评估哪些值得投，再对选中的批量生成简历。
> 与工具 A 的关系：A 处理单个 JD；C = 批量分诊 + 调度 A 的规则 + 可读性标准 + 跨简历一致性 + 合并回灌。单个 JD 直接用 A。
> 版本：v1.0 · 2026-10-20 · 对齐 master\v2.0-draft（01 v1.0 / 02 v3.0 / 03 v4.x / 05 v1.0）及工具 A v1.0

  - 文件夹：`C:\Users\surface\resumes\applications\_batches\[YYYY-MM-DD]_[label]\inbox\`，每份 JD 一个 `.md` / `.txt`

## 2. 阶段一：批量分诊（每份 JD 轻量处理，不写简历）

对每份 JD 并行执行（可用子代理，每份一个，只读事实库）：

1. **提取基本信息**：公司、职位、Job ID、地点、合同类型、截止日期；提取不到的标"待确认"。
2. **与已有申请查重**：扫描 `applications\` 下是否已有同公司或同职位的目录；有则提示，并说明可否复用其简历作底稿。
3. **分类**：Family（ATL / SM / TPM）× Lens（BNK / INT），写出判断依据（05 §2）。
4. **Fast-reject 与 Eligibility**（05 §3–§4）：命中任何一项都单列。重点核对工作准证 / PR、强制认证（PMP、TOGAF、AWS 等）、银行年限、语言、地点。
5. **Required 要求逐项对照证据**（05 §5），统计 Direct / Transferable / Gap / Unverified 各几项，列出**阻断项**（没有证据且 JD 写明必须的）。
6. **定性档位**（不打分、不给百分比、不估面试概率，D-03）：

   | 档位 | 含义 |
   |---|---|
   | **A** | Required 基本都有 Direct 或强 Transferable，无 Eligibility 缺口，定位清晰 |
   | **B** | 可投，但有明确 gap，需要靠定位和措辞诚实处理 |
   | **C** | 勉强：定位偏离我的主线，或多项 Required 只有弱证据 |
   | **X** | 建议不投：命中 fast-reject、Eligibility 缺口，或需要我没有的核心领域 |

   档位必须写理由，并注明依据哪几条证据。
7. **建议简历方案**：用哪个 Family × Lens；底稿取自哪个已有申请或 `Resumes\` 下哪份 LIB V5；预计工作量（可直接微调 / 需重新取材）。

**汇总输出 `Batch_Triage.md`**：

| # | 公司 | 职位 | 档位 | Family×Lens | Required 证据统计 D/T/G/U | 阻断项 | Eligibility 风险 | 与旧申请重复 | 建议动作 |
|---|---|---|---|---|---|---|---|---|---|

同时给出：
- **共性问题表**（借鉴 `/resume-tailoring` 的聚合缺口做法）：多份 JD 共同涉及的未决事实合并成一条，标注涉及哪几份 JD，只问我一次。每条附"不回答时的默认处理"。
- **批次观察**：这批 JD 的定位是否分散？是否值得集中精力在其中 2–3 份？（只给判断依据，不替我决定。）

**★ 审批门 C1**：我选择进入下一阶段的 JD（可调整档位建议）、回答共性问题。`triage` 模式到此结束。

## 3. 阶段二：批量定位与取材

对选中的 JD，**用一张"定位卡"一次呈现**，不逐份打断我：

| 项 | 内容 |
|---|---|
| Headline | 取自 02 §7，写明是否针对本 JD 调整 |
| Summary 主线 | 一句话叙事主线 + 对位 JD 的哪 2–3 个 Required |
| Selected Achievements | 6–8 条，按 ID 排序，写明为什么放这条 |
| 压缩 / 省略 | 哪些经历压缩或省略，原因 |
| Gap 处理 | 每个 gap 的诚实写法，禁止把 Transferable 写成 Direct |
| 关键词映射 | JD 原词 → 记录中的词 → 证据 ID（有证据才用） |
| 待我确认 | 只列会改变定位或事实的问题 |

**★ 审批门 C2**：我逐份确认或调整定位卡。

## 4. 简历可读性标准

**R1–R5 已写入事实库规则（2026-10-20，D-13），按其执行，本文件不再重复：**
- 三类读者（HR、用人经理、ATS）、首页回答三问、JD 前 5 项 Required 在首页有证据、通俗语言 → `01 §6A`
- Bullet 长度与结构、数字个数 → `01 §6` 的 Bullets / Numbers 行
- 拼写（英式，新加坡标准；JD 目标职位名按原文引用）、Summary 长度（约 3 个短段）→ `01 §6` 的 Spelling / Summary length 行
- 版面限值（bullet ≤3 行、段落 ≤4 行、首页构成）与渲染检查 → `04 §3A`、`04 §6`

阈值标 🔶。渲染结果超限、又无法在不丢失 locked 措辞或限定词的前提下压缩时，列入汇报交我决定，不得为凑限值删除限定词。

**R6 冷读测试（Cold-read）— 每份终稿必做（本工具专有；01 §8 暂未收录）**
- 另起**独立子代理**，只提供：渲染后的简历 PDF（文本或页面图像）+ 该 JD。**不提供事实库、不提供起草过程。**
- 让它依次扮演：
  (a) **Recruiter，限时 30 秒**：他是谁、什么层级、最近的角色；与 JD 最匹配的 3 点；最大疑虑；哪些句子读不懂或过于技术。
  (b) **Hiring manager，约 3 分钟**：能否胜任、有无硬伤、会追问什么、是否愿意面试。
- 判定：Recruiter 说不出 3 条匹配点，或指出超过 2 处读不懂，必须回改。
- **冷读意见只用于措辞、排序和删减，不得引入新事实。** 如果意见涉及我没有记录的事实，转为回灌候选项，由我决定。冷读评审员的意见是可读性证据，不是事实证据。
- 写入每份申请目录的 `Readability_ColdRead.md`。

## 6. 阶段四：逐份独立审计

每份草稿各派一个**审计子代理**（与起草子代理不是同一个）：

- 事实与质量审计：执行工具 A §5 的全部要求（逐条 claim 审计、01 §9 QA 清单、PDF 实际渲染检查）。
- 可读性：执行 §4 的 R6 冷读测试，并按 04 §6 在渲染 PDF 上检查 bullet / 段落限值与首页构成。
- FAIL 必须修正或删除；REVIEW 列出交我决定；没有实际渲染检查就明说"未验证"。

## 7. 阶段五：跨简历一致性检查（批量专有）

同一批简历会由不同的 HR 和猎头看到，甚至互相比对，背调更会交叉核对。把本批所有简历，以及 `applications\` 下已有的历史简历，抽取成一张对照表：

| 事实项 | 简历 1 | 简历 2 | … | 历史简历 | 事实库值 | 是否一致 |
|---|---|---|---|---|---|---|
| 各段职位名 / 日期 | | | | | 02 §2 | |
| 团队规模 | | | | | 03 §0A | |
| 关键数字 | | | | | 03 §0A | |
| 所有权动词（同一成就） | | | | | 03 / 01 §4 | |
| Headline、联系方式、姓名写法 | | | | | 02 §1, §7 | |

- 不一致且不是 Lens 造成的有意取舍，必须修正。
- 与已投递的历史简历不一致的，单列提示（可能涉及背调风险），由我决定是否需要补充说明。
- 输出 `Batch_Consistency_Check.md`。

**★ 审批门 C3**：交付各份红字草稿 + 审计报告 + 冷读结果 + 一致性表。我逐份确认或修改；批准后生成全黑终稿 `wilson-2026_[Family]_[Lens]_[Company]_V1_0_0.docx` 和 PDF。

## 10. 异常处理

- 某份 JD 读取失败（登录墙等）：标"待补充"，请我粘贴文本，不阻塞其他 JD。
- 某份 JD 内容过短：照常分诊，标"JD 不完整"，档位只能给到 B 或以下。
- 超过并发上限：分批执行，先做档位 A、再做 B。
- 渲染检查无法执行：明说"未验证"，不得声称版面已检查。
- 子代理之间的结论冲突：并列呈现，交我决定，不自行取舍。
